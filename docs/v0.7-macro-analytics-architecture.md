# MacroVision v0.7 Macro Analytics Engine architecture

Status: Phase 1 planning proposal

Baseline: MacroVision 0.6.0, Alembic head `20260724_0008`

Scope: documentation only; no schema, API, or runtime behavior is introduced

## Phase 2B implementation clarifications

- Input position 0 exclusively owns the non-synthetic output timeline. Only its exact,
  eligible observation timestamps inside the inclusive requested range are candidates.
- Formula-role lineage positions are deterministic: current point `0`;
  previous-period/YoY anchor `0` and current `1`; rolling oldest `0` through newest
  `window - 1`; rebase base `0` and current `1`. Identical rebase timestamps retain both
  roles.
- `snapshot_fingerprint` includes the effective calculation cutoff and therefore
  identifies the cutoff-bound resolution event. `reusable_fingerprint` excludes only
  the non-semantic acquisition cutoff and identifies identical resolved source
  semantics.
- PostgreSQL execution establishes `REPEATABLE READ` before its first definition/time
  statement. SQLite uses bounded `BEGIN IMMEDIATE`; this deliberately trades increased
  write contention for a stable source snapshot in both WAL and rollback-journal modes.
- A range with no eligible primary-source observations succeeds with zero outputs and
  zero lineage links.
- `inputs_examined` counts every concrete required source point slot evaluated,
  including absent slots. An impossible calendar anchor has no concrete slot.

## Executive summary

MacroVision v0.7 should add a deterministic analytical layer over data already held by
the Macro Data Engine. It must never fetch provider data, execute user code, produce
trading signals, or treat a later revision as if it had been known earlier.

The recommended design is a **hybrid materialization model**:

- immutable, versioned calculation definitions describe meaning;
- bounded runs resolve an input snapshot at one UTC knowledge cutoff;
- results and point-level source lineage are persisted;
- read endpoints serve persisted results rather than recalculating implicitly;
- active requests, resolved snapshots, and reusable successful results have distinct
  private deterministic fingerprints.

The safest initial execution strategy is **bounded synchronous execution** through an
explicit run endpoint. Analytics must not be added to the provider scheduler in v0.7.
The schema should permit a later, separate analytics worker that reuses extracted
claim/lease/fencing primitives without inheriting provider retry or network semantics.

The primary no-look-ahead rule is:

> A calculation may use only source observations whose ingestion timestamp is at or
> before the run's UTC knowledge cutoff, and only revisions whose revision timestamp is
> at or before that cutoff. Provider vintage and publication fields are provenance, not
> substitutes for MacroVision's knowledge time.

## Repository audit

### Existing invariants to reuse

| Area | Current implementation | Reusable invariant |
| --- | --- | --- |
| Exact values | `persistence_types.ScaledDecimal` and Macro Data's scale 8 | Accept `Decimal` only, persist signed scaled 64-bit integers, round half-even |
| Time | `UTCDateTime` and `contracts.utc_timestamp` | Reject naive inputs, normalize to UTC, use PostgreSQL `TIMESTAMPTZ`, adapt SQLite safely |
| Observation identity | Unique `(series_id, observed_at)` | One stable observation row per series timestamp |
| Revisions | Immutable `DataRevision` rows with sequence and prior/revised states | Never overwrite published history; reconstruct effective state by cutoff |
| Missing data | Explicit `ObservationStatus.missing` with null value | Never encode missing data as zero or a magic number |
| Vintage provenance | Provider vintage dates stored separately from ingestion/publication time | Vintage date describes provider state; ingestion time describes system knowledge |
| Referential safety | Audit foreign keys use `RESTRICT`; relationships avoid delete cascades | History cannot disappear through ordinary parent deletion |
| Concurrency | Unique constraints plus optimistic `lock_version` on mutable aggregates | Translate stale writes and integrity races to controlled 409 responses |
| API errors | Shared 404, 409, and bounded 422 response bodies | Analytics should use the same public error envelope |
| Lists | `limit` 1–200, non-negative `offset`, deterministic tie-breakers | Apply to every analytics collection |
| Imports/providers | Fingerprinted idempotency and immutable batch history | Hash normalized private inputs; never expose internal hashes |
| Scheduler | Durable runs, leases, generation fencing, concurrency keys, deterministic retry | Potential future primitives, not a provider-specific analytics queue |

The current as-of implementation filters observations by
`DataObservation.ingestion_timestamp <= as_of`, then selects the last revision ordered
by sequence whose `revision_timestamp <= as_of`. The effective read returns that
version's publication, ingestion/revision time, provider vintage, value, status, and
source reference. That behavior is the source-snapshot authority for analytics.

Macro Data values serialize as fixed eight-decimal strings. SQLite and PostgreSQL use
the same integer representation for values, while timestamps are stored as naive UTC in
SQLite and aware UTC in PostgreSQL. Existing migration tests exercise every historical
revision, seeded legacy data, metadata consistency, and downgrade/re-upgrade.

The provider scheduler owns provider series snapshots, import-batch results, network
retry classification, at-least-once execution, lease recovery, and one-running-job
concurrency keys. PostgreSQL claims use `FOR UPDATE SKIP LOCKED`; SQLite depends on
coarse write serialization and guarded updates. Completed runs are immutable.

### Architectural gaps

1. There is no stable analytical definition identity separated from immutable semantic
   versions.
2. Existing as-of reads expose effective values but not the exact revision identity
   chosen for every point; analytics needs an internal snapshot resolver that returns
   both.
3. Provider runs cannot represent transformation parameters, multiple ordered inputs,
   analytical lineage, or derived counters without becoming a mixed-purpose aggregate.
4. No calculation context, output quantization contract, transformation registry, or
   dependency-cycle rule exists.
5. Offset pagination is consistent today but can shift under concurrent inserts; every
   analytics list therefore needs deterministic ordering and documented snapshot limits.
6. ORM immutability hooks protect normal application paths but raw SQL remains capable
   of bypassing them. Database constraints and restricted privileges remain necessary.

### Boundaries

The new engine should use separate modules:

- `analytics_models.py`: analytics persistence only;
- `analytics_schemas.py`: public validation and serialization;
- `analytics_transformations.py`: code-defined pure transformation registry;
- `analytics_services.py`: snapshots, validation, idempotency, execution, and lineage;
- `analytics_api.py`: HTTP translation only.

It may import Macro Data models and a small public snapshot service. Macro Data,
provider, and scheduler modules must not import analytics modules. This one-way
dependency prevents cycles and keeps provider acquisition independent of interpretation.

## Goals and non-goals

### Goals

- Calculate deterministic derived economic series from stored Macro Data.
- Reproduce current and historical calculations without future-revision leakage.
- Preserve every calculation definition, run, output vintage, and source lineage.
- Support exact arithmetic consistently on SQLite and PostgreSQL.
- Reject incompatible inputs rather than silently resampling or coercing them.
- Bound CPU, memory, database growth, request size, and public error content.

### Non-goals

- Provider retrieval, scheduling provider synchronization, or web scraping.
- Arbitrary expressions, Python, SQL, plug-in code, or user-supplied executables.
- Interpolation, forward/back fill, resampling, seasonal adjustment, or FX conversion.
- Forecasting, AI/LLM analysis, regime classification, recommendations, signals, orders,
  brokers, authentication, or a frontend.
- Cross-frequency transformations in the first release.

## Domain terminology

- **Definition**: stable identity and mutable display metadata for one derived series.
- **Definition version**: immutable calculation meaning, inputs, and parameters.
- **Knowledge cutoff (`as_of`)**: UTC instant limiting facts available to a run.
- **Calculation cutoff**: explicit `as_of`, or one UTC instant captured at run start for
  a current calculation. It never advances during that run.
- **Input version**: an observation's original state or one exact revision selected at
  the cutoff.
- **Run**: immutable request/snapshot/result record for one definition version, date
  range, cutoff, and engine version.
- **Derived observation**: immutable persisted output point, including explicit missing
  status where the evaluation domain contains a timestamp but cannot produce a value.
- **Lineage**: immutable links from one output point to every exact input observation
  and selected revision.
- **Calculation engine version**: code-owned identifier that changes whenever arithmetic,
  alignment, missingness, or canonicalization semantics change.

## Analytical invariants

### No-look-ahead and vintage semantics

1. Every run persists one explicit `calculation_cutoff`. For a current request, the
   database and transaction-snapshot protocol below obtain it; caller-provided `as_of`
   is normalized to UTC and becomes the cutoff for an historical request.
2. A source observation is eligible only when its `ingestion_timestamp <= cutoff`.
3. Its effective version is the greatest revision sequence whose
   `revision_timestamp <= cutoff`; absent such a revision, the original state applies.
4. Revisions after the cutoff are invisible even if their observation date,
   publication timestamp, or provider vintage predates the cutoff.
5. `provider_vintage_start/end` and `publication_timestamp` remain lineage provenance.
   They never make a row known before ingestion.
6. All source series are resolved in one database transaction. The resolver returns the
   exact observation ID, selected revision ID (null for original), value/status, and
   knowledge timestamp. A source revision outside the established snapshot cannot enter
   midway through that run.
7. On PostgreSQL, Phase 2B begins a `REPEATABLE READ` transaction. Its first statement
   loads the definition/version, acquires the transaction snapshot, and calls
   `statement_timestamp()` in that same `SELECT`. That exact value—not
   `CURRENT_TIMESTAMP`, `transaction_timestamp()`, or `clock_timestamp()`—is the
   persisted cutoff and governs every eligibility
   predicate, so every visible row necessarily precedes or equals the recorded knowledge
   upper bound. Tests must commit a competing revision before, during, and after snapshot
   acquisition and prove the exact boundary.
8. On SQLite, Phase 2B uses bounded `BEGIN IMMEDIATE`, then invokes the
   connection-registered `macrovision_utc_now()` function in the first definition read.
   The function returns canonical UTC with six decimal places and avoids SQLite's
   whole-second `CURRENT_TIMESTAMP` and floating-point Julian-day arithmetic. WAL and
   rollback-journal tests prove a concurrent revision cannot enter midway. This clock
   assumes each application process has a correctly synchronized host UTC clock; the
   write lock provides database consistency, not cross-host clock synchronization.
9. The cutoff is an eligibility upper bound; persisted exact lineage is the replay
   authority. Provider vintage and publication timestamps never substitute for it.
   Implementation must not begin until these concurrency tests are designed.
10. Historical replay uses the persisted cutoff, definition version, engine version, and
   exact lineage. It does not reinterpret a run using current source state.

Eligible revisions are ranked in SQL with `row_number()` partitioned by observation and
ordered by sequence then ID descending. Only rank one is materialized, bounding each
batch to at most one revision per observation without allocating revision history in
Python. Process-control exceptions (`KeyboardInterrupt`, `SystemExit`, and
`GeneratorExit`) roll back and escape unchanged; they do not create failed-run audit
records.

Provider vintage dates can be useful for display and research, but they are not precise
availability timestamps. An optional future policy may constrain provider vintages in
addition to knowledge time; it must be a new immutable definition version.

### Input alignment

- All inputs must have the same declared regular frequency. `irregular` is rejected.
- v0.7 performs no resampling, aggregation, interpolation, or timezone bucketing.
- Timestamps must be exact UTC matches for multi-input operations.
- The evaluation domain is the ordered union of eligible primary-input timestamps in
  the requested output range. Missing secondary timestamps produce explicit missing
  outputs, not dropped rows.
- Unary operations evaluate the eligible source timestamps. An explicit source
  `missing` state yields an explicit missing derived point.
- Ordering is always `(observed_at, observation_id)` for source selection and
  `(observed_at, derived_observation_id)` for results.
- Rolling windows contain the current point and preceding exact-frequency points.
  Windows are complete only when all required calendar anchors exist and are present.
- Partial windows are not emitted as values. They produce `missing` with reason
  `insufficient_history`.
- Required history is read before `requested_start`, but output remains restricted to
  `[requested_start, requested_end]`.
- YoY anchors are: daily = same month/day in the previous year; weekly = exactly 52
  weeks earlier; monthly = 12 months earlier; quarterly = 4 quarters earlier; annual =
  one year earlier. February 29 without a February 29 prior-year anchor is missing.
  Missing exact anchors are never replaced by a nearby date.

### Missing values

Derived points have `present` or `missing` status. Missing rows have null values and a
bounded code from: `source_missing`, `timestamp_absent`, `insufficient_history`,
`division_by_zero`, `non_finite_result`, or `numeric_overflow`.

- No forward fill, backward fill, interpolation, or zero substitution.
- A missing input makes the dependent point missing.
- Division by zero makes only that point missing.
- A non-finite intermediate or unrepresentable output makes the point missing and
  increments the run's issue counter; it never persists a sentinel.
- Structural errors (invalid parameters, incompatible metadata, cycles) reject creation
  or fail the run atomically rather than creating a misleading series.

### Units and dimensions

- `difference`, `spread`, moving average, and rolling standard deviation preserve the
  input unit and currency. Two-input subtraction requires identical unit and currency.
- Ratio requires equal dimensions, unit, and currency and emits unit `ratio` with no
  currency. This yields a dimensionless value; cross-unit and cross-currency ratios are
  rejected in v0.7.
- Percent change and YoY percent change emit unit `percent` and no currency.
- Rolling z-score emits unit `z_score` and no currency.
- Rebase emits unit `index` and no currency.
- All multi-input transformations require identical geography, frequency, and seasonal
  adjustment. Unknown adjustment is compatible only with unknown.
- Display labels do not establish dimensional compatibility. The immutable version
  stores validated source metadata snapshots so later mutable source metadata cannot
  silently change historical meaning.

### Numeric precision

- Inputs and parameters must be `Decimal`; floats are rejected at schema and service
  boundaries.
- Persisted outputs use `ScaledDecimal(8)`, matching Macro Data:
  range `[-92233720368.54775808, 92233720368.54775807]`.
- Each run uses an isolated decimal context with precision 38, `ROUND_HALF_EVEN`, and
  traps for invalid operations, division by zero, and overflow.
- Addition, subtraction, multiplication, division, mean, square, and square root use
  that context. Only the final point is quantized to `0.00000001`, half-even.
- Transformation parameters are canonical fixed-point strings, never JSON numbers.
- PostgreSQL and SQLite persist the same scaled integer. The engine, not a database
  aggregate function, performs arithmetic to avoid backend-dependent rounding.

## Transformation contracts

All examples show the final eight-decimal result. Parameters not listed are rejected.
Every registry entry declares arity, parameter schema, compatibility validator, history
calculator, and pure evaluator.

### `difference`

- Inputs: one; parameters: none.
- Formula: `y(t) = x(t) - x(previous_period)`.
- History: one exact preceding period; alignment follows input frequency.
- Unit: input unit and currency.
- Missing: either point missing/absent yields missing; no denominator.
- Example: `105.25 - 100.00 = 5.25000000`.

### `percent_change`

- Inputs: one; parameters: none.
- Formula: `y(t) = ((x(t) / x(previous_period)) - 1) * 100`.
- History: one exact preceding period.
- Unit: percent, currency null.
- Missing: absent/missing point yields missing; prior value zero yields
  `division_by_zero`.
- Example: `((110 / 100) - 1) * 100 = 10.00000000`.

### `year_over_year_percent_change`

- Inputs: one; parameters: none.
- Formula: `y(t) = ((x(t) / x(yoy_anchor(t))) - 1) * 100`.
- History: the frequency-specific YoY anchor defined above.
- Unit: percent, currency null.
- Missing: an absent/missing anchor yields missing; zero anchor yields
  `division_by_zero`.
- Example: monthly `120 / 100` gives `20.00000000`.

### `ratio`

- Inputs: two ordered aliases `numerator`, `denominator`; parameters: none.
- Formula: `y(t) = numerator(t) / denominator(t)`.
- History: none beyond aligned current points.
- Unit: ratio, currency null; inputs must be dimensionally identical.
- Missing: absent/missing aligned input yields missing; denominator zero yields
  `division_by_zero`.
- Example: `150 / 200 = 0.75000000`.

### `spread`

- Inputs: two ordered aliases `minuend`, `subtrahend`; parameters: none.
- Formula: `y(t) = minuend(t) - subtrahend(t)`.
- History: none; exact timestamp alignment.
- Unit: shared input unit and currency.
- Missing: absent/missing aligned input yields missing.
- Example: `5.25 - 3.75 = 1.50000000`.

### `moving_average`

- Inputs: one; parameter: integer `window` in `[2, 1000]`.
- Formula: `y(t) = sum(window values) / window`.
- History: `window - 1` exact preceding periods; full windows only.
- Unit: input unit and currency.
- Missing: any absent/missing member yields `insufficient_history` or
  `source_missing`; no partial average.
- Example: window 3 over `10, 20, 30` gives `20.00000000`.

### `rolling_standard_deviation`

- Inputs: one; parameter: integer `window` in `[2, 1000]`.
- Formula: population standard deviation
  `sqrt(sum((x(i) - mean)^2) / window)`.
- History: `window - 1`; full windows only.
- Unit: input unit and currency.
- Missing: any absent/missing member yields missing.
- Example: window 2 over `2, 4` has mean 3 and gives `1.00000000`.

### `rolling_z_score`

- Inputs: one; parameter: integer `window` in `[2, 1000]`.
- Formula: `(x(t) - population_mean(window)) / population_stddev(window)`.
- History: `window - 1`; full windows only.
- Unit: z_score, currency null.
- Missing: incomplete/missing window yields missing; zero standard deviation yields
  `division_by_zero`.
- Example: window 2 over `2, 4`: `(4 - 3) / 1 = 1.00000000`.

### `rebase_index`

- Inputs: one; parameters: aware UTC `base_timestamp` and positive Decimal
  `base_value` defaulting to `100.00000000`.
- Formula: `y(t) = x(t) / x(base_timestamp) * base_value`.
- History: exact base timestamp must be eligible at the run cutoff, even if before the
  requested output range.
- Unit: index, currency null.
- Missing: missing/absent base makes the run invalid; zero base produces a controlled
  validation failure; missing point produces missing.
- Example: base `80`, current `100`, base value `100` gives `125.00000000`.

## Domain model and proposed database schema

### `DerivedSeriesDefinition`

Stable public identity and mutable display/lifecycle fields:

- `id`, canonical unique `code`;
- `title` (1–240), bounded `description`;
- `enabled`, `lock_version`, `created_at`, `updated_at`.

`code` accepts ASCII only, is normalized to uppercase before persistence, and must match
`^[A-Z][A-Z0-9_.-]{0,119}$`. A database `CHECK` enforces that canonical uppercase syntax
and one ordinary unique constraint owns uniqueness, so `cpi.yoy` and `CPI.YOY` cannot
coexist differently on SQLite and PostgreSQL. Only title, description, and enabled state
may change through guarded services. `lock_version > 0`; updates require
`expected_lock_version`. Disabling does not delete definitions, versions, runs, or
outputs. Index `(enabled, code, id)`.

### `DerivedSeriesDefinitionVersion`

- `id`, `definition_id RESTRICT`, positive `version`;
- code-owned `transformation_type`;
- canonical bounded `parameters` JSON and private `parameters_fingerprint`;
- output `unit`, `frequency`, `geography`, nullable `currency`,
  `seasonal_adjustment`;
- `engine_contract_version`, `created_at`, optional bounded `change_note`;
- unique `(definition_id, version)`, index `(definition_id, version DESC, id DESC)`.

Rows are immutable and undeletable. Versions are positive and strictly monotonic. The
current version is always the row with the highest `(version, id)`, not a mutable
pointer. Under `expected_lock_version`, the service locks or conditionally updates the
definition, computes `next_version = previous_max + 1`, inserts the version and all
inputs, and increments the definition lock exactly once. Unique
`(definition_id, version)` protects races. Current reads order by
`version DESC, id DESC`. Semantic rollback creates a new version copying older
semantics; history is never made current by moving a pointer backward. This removes a
circular migration dependency, makes SQLite/PostgreSQL schema behavior identical,
preserves immutable history, and allows historical active-version inference from
version creation times.

### `DerivedSeriesInput`

- `id`, `definition_version_id RESTRICT`;
- `position` (zero-based), unique bounded `alias`;
- `source_series_id RESTRICT`;
- snapshots of source code, unit, frequency, geography, currency, and seasonal adjustment.

Unique `(definition_version_id, position)` and `(definition_version_id, alias)`;
index on the source FK. Phase 2A allows only Macro Data `DataSeries` inputs.
Derived-to-derived columns are deferred entirely until dependency-cycle, ordering, and
depth semantics are designed.

### `AnalyticsRun`

- `id`, `definition_version_id RESTRICT`;
- `status`: pending, running, succeeded, failed;
- requested inclusive `start_at`, `end_at`; persisted `calculation_cutoff`;
- `engine_version`; private `request_fingerprint`, `snapshot_fingerprint`, and nullable
  `reusable_fingerprint`, each 64-character lowercase SHA-256 hex;
- counters: inputs examined, outputs present, outputs missing, lineage links;
- `created_at`, `started_at`, `completed_at`;
- bounded `error_code` and sanitized `error_message`;
- optional `retry_of_run_id RESTRICT`.

Completed and failed rows are immutable. A partial unique index on
`request_fingerprint` where status is pending/running prevents an exact request from
being active twice. `snapshot_fingerprint` is retained on succeeded and failed attempts
but is not globally unique. A partial unique index on `reusable_fingerprint WHERE
reusable_fingerprint IS NOT NULL` permits exactly one successful reusable result while
failed attempts reserve nothing. Indexes:
`(definition_version_id, created_at DESC, id DESC)`,
`(status, created_at, id)`, and `(calculation_cutoff, id)`.

### `DerivedObservation`

- `id`, `run_id RESTRICT`, `definition_version_id RESTRICT`;
- `observed_at`, `value ScaledDecimal(8)` nullable, `status`;
- nullable bounded `missing_reason`, `created_at`;
- unique `(run_id, observed_at)`;
- indexes `(definition_version_id, observed_at, id)` and `(run_id, observed_at, id)`;
- status/value and status/reason check constraints.

Rows are immutable. A source change creates a new run and new output vintage; it never
updates prior output points.

### `DerivedObservationLineage`

- `id`, `derived_observation_id RESTRICT`;
- non-null `input_position`, non-null `source_observation_id RESTRICT`;
- nullable `source_revision_id RESTRICT`;
- non-null `source_version_kind` (`original` or `revision`);
- non-null `source_version_id` and non-null `lineage_position`;
- selected `source_knowledge_timestamp`;

For an original value, `source_revision_id IS NULL`,
`source_version_kind = 'original'`, and
`source_version_id = source_observation_id`. For a revision,
`source_revision_id IS NOT NULL`, `source_version_kind = 'revision'`, and
`source_version_id = source_revision_id`. Database `CHECK` constraints enforce both
shapes. `lineage_position` is zero for a non-window point; rolling members use
deterministic positions `0..window-1`.

Unique `(derived_observation_id, input_position, source_version_kind,
source_version_id, lineage_position)` contains no nullable column, so uniqueness is
identical in SQLite and PostgreSQL. Index both source FKs and
`(derived_observation_id, input_position, lineage_position, id)`. Lineage is immutable.

### Lifecycles and deletion

No history-bearing row cascades on delete. Definitions are disabled, not deleted after
versions exist. Versions, inputs, runs, outputs, and lineage are immutable. ORM hooks
provide immediate application feedback; database `RESTRICT`, checks, uniqueness, and
least-privilege production roles provide the durable boundary.

## Materialization decision

| Option | Advantages | Rejection/role |
| --- | --- | --- |
| Virtual on read | Low storage, always appears current | Reject: cannot prove historical inputs, costly reads, revisions silently change answers |
| Fully materialized automatically | Fast and auditable | Reject for v0.7: unbounded recomputation and scheduler coupling |
| Hybrid persisted explicit runs | Auditable, reproducible, bounded, cacheable | **Choose** |

The hybrid model persists explicit calculation vintages and lineage but calculates only
on a bounded request. Latest reads select the newest succeeded run for the current
definition version using `(calculation_cutoff DESC, completed_at DESC, id DESC)`.
Historical as-of reads select the newest succeeded run whose calculation cutoff is at
or before the requested cutoff; they never synthesize a result from later runs.

Retention must be explicit. Do not delete historical runs automatically in v0.7.
Measure growth first. A future archive policy may compact redundant lineage only if it
preserves exact reconstructability and requires an independently reviewed migration.

## Idempotency and lineage

Canonicalization uses UTF-8 JSON with sorted keys, fixed separators, UTC timestamps in
`YYYY-MM-DDTHH:MM:SS.ffffffZ`, fixed-point Decimal strings, ordered input positions,
and no environment-dependent values.

All three identities are private, 64-character lowercase SHA-256 hex values. They are
never public, logged, or returned:

1. `request_fingerprint` is normalized from the definition version, requested start/end,
   explicit calculation cutoff, and engine contract version. It prevents duplicate
   pending/running work for the exact same request through its active partial unique
   index.
2. `snapshot_fingerprint` is calculated only after source resolution from the definition
   version and semantic fingerprint, ordered source series, every selected observation
   and exact original/revision identity, requested range, cutoff, canonical
   transformation parameters, and engine version. It audits the exact resolved snapshot,
   remains on succeeded and failed attempts, and is deliberately not globally unique.
3. `reusable_fingerprint` is calculated from that completed semantic snapshot. It is
   nullable, set only when a run succeeds, and uniquely indexed only where non-null.
   Failed runs cannot reserve a reusable identity, so their retries may succeed with the
   same result identity.

No caller-provided idempotency key is needed or stored. Internal fingerprints never
appear in responses or logs. An active race returns the existing active run when safe
or 409. In a successful race, the loser rolls back every output and lineage row and
returns the winning run. Failed attempts retain request and snapshot audit identities;
`retry_of_run_id` links a retry without weakening either run's immutability.

Each output point links to all exact inputs used, including every rolling-window member.
Run counters must equal persisted rows and links. Snapshot resolution, run claim,
outputs, lineage, and terminal status use deliberate transaction boundaries so a
failed calculation leaves no partial output graph.

strings, aware UTC timestamps, `limit` default 100/max 200, `offset` default 0, and
deterministic ID tie-breakers. Fingerprints, raw snapshots, lease fields, and internal
exception details are private.

| `GET /derived-series/{id}/observations/latest` | highest/current definition version only | 200 point plus selected version metadata | 404 |
| `GET /derived-series/{id}/observations` | start/end, optional run_id or `definition_version`; defaults to highest version | 200 ordered points plus version metadata | 404, 422 |
| `GET /derived-series/{id}/observations/as-of` | aware as_of, range, optional exact `definition_version`; otherwise highest version created by cutoff | 200 persisted points plus selected version metadata | 404, 422 |

Create/version schemas carry full typed transformation parameters using a discriminated
union, not arbitrary dictionaries. Responses include definition/version IDs, public
metadata, status, cutoff, engine version, counters, and timestamps. They exclude
all run/parameter fingerprints, raw errors, and internal concurrency
data. Every new version becomes current atomically and can never be moved backward, so
`created_at` is its activation time. `/latest` and ordinary observations default to the
highest version. As-of reads choose the highest version whose `created_at <= as_of`
unless an explicit `definition_version` requests exact replay. If that version has no
succeeded run with `calculation_cutoff <= as_of`, return 404. Never substitute a run
from a later version and never calculate implicitly during a read.

The public/private boundary is explicit. Definition versions expose typed parameters,
server-derived output metadata, bounded change notes, and immutable source metadata
snapshots. Run responses expose status, range, cutoff, engine version, counters,
timestamps, and bounded safe failure fields. Public schemas never expose
`parameters_fingerprint`, `request_fingerprint`, `snapshot_fingerprint`,
`reusable_fingerprint`, canonical preimages, ORM relationships, SQL, Python expressions,
or executable formulas.

Definition metadata and enable/disable operations use a conditional
`expected_lock_version` update and increment the aggregate lock exactly once. Version
creation first derives every snapshot and output field server-side, conditionally
increments the same definition lock, calculates `max(version) + 1`, and inserts the
immutable version plus ordered inputs in one transaction. The unique definition/version
constraint remains the final race guard.

Ordinary range reads select one exact run. Without `run_id`, they select the latest
succeeded run for one exact version whose requested range covers the requested range.
They never stitch partial runs. Historical reads select the highest version created by
the requested `as_of` unless an exact version is requested, then choose one succeeded
run with `calculation_cutoff <= as_of`. This is knowledge-cutoff replay; it does not
claim the run physically existed at the historical instant.

All list and page endpoints use `limit` 1–200 and `offset >= 0`. Definitions order by
code then ID, versions by version then ID descending, runs by creation time then ID
descending, observations by observation time then ID, and lineage by input position,
lineage position, then ID.

## Scheduler and worker decision

### Decision

Keep v0.7's first release synchronous and bounded. The explicit run endpoint creates
and completes a run in one service operation, with a configured timeout/range/point
budget. It does not invoke providers and does not reuse `ProviderSyncRun`.

### Rationale

- Provider retries classify HTTP/provider failures; analytical failures are deterministic
  validation, resource, or source-snapshot conflicts.
- Provider concurrency keys represent provider+series synchronization; analytics keys
  represent definition version+snapshot.
- Adding job types to current tables would weaken check constraints, immutability rules,
  result columns, and operational observability.
- Dependency ordering after synchronization is not yet specified. Automatic recompute
  could amplify every source revision into unbounded work.
- SQLite's coarse serialization makes a second worker workload especially contentious.
- PostgreSQL `SKIP LOCKED`, leases, and generation fencing are useful patterns, but must
  be extracted into shared primitives before reuse.

Phase 3 may add a separate `analytics_worker` and analytics-specific queue/run state if
measurements show synchronous bounds are insufficient. It should reuse tested claim and
fencing algorithms, retain separate tables and retry policy, and enqueue recomputation
explicitly after a successful provider import rather than infer dependencies inside the
provider transaction. At-least-once delivery remains safe because the request and
reusable fingerprints plus database uniqueness make completion idempotent.

## Migration plan

The next migration should follow `20260724_0008`; this document deliberately assigns no
revision identifier or file.

Creation order:

1. `derived_series_definitions`;
2. `derived_series_definition_versions`;
3. `derived_series_inputs`;
4. `analytics_runs`;
5. `derived_observations`;
6. `derived_observation_lineage`;
7. constraints and indexes.

All history FKs use `ON DELETE RESTRICT`. Mutable definition metadata also retains
history; no cascade is permitted. The migration must use SQLAlchemy types compatible
with SQLite and PostgreSQL, `UTCDateTime`-equivalent aware columns, scaled `BIGINT`
values, bounded strings/JSON, and dialect-specific partial-index predicates where
needed. Avoid native enums unless their full PostgreSQL lifecycle is owned and tested.

Downgrade order is the exact reverse: constraints/indexes, lineage, observations, runs,
inputs, versions, definitions. There is no `current_version_id`, circular FK, or
post-create definition alteration. Drop dependent indexes/constraints before tables and
owned PostgreSQL types after dependants. Required gates are base-to-head,
head-to-base-to-head, upgrades from every legacy revision, seeded v0.1–v0.6
compatibility, metadata consistency, PostgreSQL enum/type cleanup, and preservation of
all pre-existing rows.

## Threat model and proposed limits

| Risk | Proposed mitigation / initial bound |
| --- | --- |
| Computational denial of service | max 2 inputs, 10,000 output timestamps/run, 25,000 total source points |
| Large windows | integer window 2–1,000 and total lineage-link cap 100,000 |
| Excessive range | max 10 years daily, 30 years weekly/monthly, 100 years quarterly/annual, also point cap |
| Malformed parameters | discriminated Pydantic schemas; reject unknown keys and non-Decimal numbers |
| Numeric overflow | precision-38 trapped context, scaled-int range check, explicit missing issue |
| Dependency cycles/self-reference | source DataSeries only initially; later DAG validation, max depth 8 |
| Concurrent duplicates | private fingerprint plus active/completed unique database constraints |
| Revision during calculation | one transaction snapshot and exact selected-version fingerprint |
| Lineage growth | hard links/run cap, bounded ranges/windows, measure before adding archival |
| Log/error leakage | bounded code-defined errors; no fingerprints, snapshots, values, SQL, or credentials |
| Arbitrary execution | closed code registry only; no expressions, SQL fragments, `eval`, or plug-ins |
| Misuse as a signal | neutral derived-data language; no recommendation, target, trade, or certainty fields |

Suggested future configuration names (not added in Phase 1):
`analytics_max_inputs=2`, `analytics_max_output_points=10000`,
`analytics_max_source_points=25000`, `analytics_max_window=1000`,
`analytics_max_lineage_links=100000`, `analytics_sync_timeout_seconds=30`, and

## Testing strategy

### Unit and contract matrix

- Every transformation: exact positive, negative, zero, boundary, and half-even cases.
- Missing source, absent timestamp, incomplete window, zero denominator, constant
  z-score window, non-finite operation, and scaled-integer overflow.
- Frequency, unit, currency, geography, and seasonal-adjustment incompatibility.
- Calendar anchors for daily leap day, weekly, monthly, quarterly, and annual YoY.
- Registry rejects arbitrary/unknown transformation and parameter fields.
- No Python float accepted anywhere in schemas, canonicalization, or evaluators.

### Service and integration matrix

- Current cutoff captured once; explicit as-of excludes later observations and revisions.
- Provider vintage predating cutoff does not admit later-ingested data.
- Source revision creates a distinct run and preserves the prior outputs.
- Identical exact snapshots replay one completed run.
- Request, snapshot, and reusable fingerprints have distinct canonical inputs and
  lifecycles; all are lowercase SHA-256 and remain private.
- A failed run does not block a retry, an active duplicate is prevented, and a
  successful race rolls back loser outputs and reuses the winner.
- Definition versions are immutable and monotonically unique under competing writes.
- Mixed-case definition codes normalize to uppercase; case-equivalent duplicates fail
  identically on SQLite and PostgreSQL.
- Metadata stale writes return 409; terminal run/output/lineage mutations fail.
- Lineage identifies original versus exact revision and every rolling member.
- Non-null lineage uniqueness and original/revision shape checks execute on SQLite and
  PostgreSQL.
- Failure rolls back every output and lineage row while retaining a bounded failed run.
- Historical reads select the version active at as-of; explicit `definition_version`
  replay never substitutes another version.
- PostgreSQL tests cover cutoff/snapshot acquisition with revisions committed before,
  during, and after the first statement.
- SQLite WAL and non-WAL tests cover concurrent revisions and the bounded
  `BEGIN IMMEDIATE` fallback if ordinary snapshot behavior cannot be proven.
- SQLite duplicate-run contention and real PostgreSQL unique races.

### API, migration, and security matrix

- Shared 404/409/422 shape and no private hashes/errors in OpenAPI or JSON.
- Deterministic pagination/order and max-limit validation.
- OpenAPI fixed-decimal strings, aware timestamps, nullability, and discriminators.
- Migration base/head cycle, every prior upgrade, legacy seeded compatibility, metadata
  consistency, constraints/indexes/RESTRICT FKs, and PostgreSQL execution.
- Log capture confirms no credentials, fingerprints, raw parameter payloads, SQL, or
  unexpected values.
- Full suite coverage gate at least 95%.

Property-based tests are valuable for arithmetic identities, Decimal serialization,
random missingness, rolling-window lengths, and canonical fingerprint stability.
Introduce a pinned offline-capable dependency only after review; deterministic
parameterized tests remain mandatory and cannot be replaced by generated cases.

## Adversarial architecture review

- **Look-ahead:** resolved by ingestion/revision cutoffs and exact selected-version
  lineage. Provider vintage is explicitly non-authoritative for availability.
- **Mutable meaning:** resolved by immutable definition versions; metadata updates cannot
  alter semantics.
- **Silent data repair:** resampling, filling, interpolation, and zero substitution are
  forbidden; missingness is explicit.
- **Numeric drift:** floats and backend aggregates are forbidden; precision, rounding,
  standard-deviation population convention, and output scale are fixed.
- **Cycles:** derived inputs are deferred initially. Future derived dependencies require
  transactionally enforced DAG/depth validation.
- **Lineage explosion:** bounded by point/window/link caps. Automatic recomputation and
  retention deletion are both deferred.
- **Backend divergence:** arithmetic stays in Python Decimal; real PostgreSQL migration,
  snapshot, and race tests remain release gates.
- **Scheduler conflict:** analytics remains outside provider run tables and retry policy.
- **Investment behavior:** the layer computes neutral historical data only and exposes no
  recommendation, prediction, confidence, allocation, or execution semantics.

## Resolved decisions and remaining implementation gates

No unresolved decision blocks Phase 2A:

- **Resolved:** lineage uses a fully non-null uniqueness key plus checked
  original/revision shapes, identical across SQLite and PostgreSQL.
- **Resolved:** derived-to-derived input columns are deferred entirely; Phase 2A stores
  only Macro Data source series.
- **Resolved:** current version is inferred from the highest immutable version; no
  current-version FK exists.
- **Resolved:** request, snapshot, and reusable identities have separate fields,
  lifecycles, and partial uniqueness.

Remaining gates do not change the Phase 2A schema:

1. **Phase 2B gate:** implement and prove the specified PostgreSQL and SQLite
   transaction-snapshot/cutoff protocols under concurrent revisions.
2. **Phase 3 gate:** benchmark synchronous limits. If 30 seconds is not reliable,
   approve a separate analytics worker rather than expanding provider tables.
3. **Out of initial scope:** derived dependency ordering, stale-output propagation, DAG
   validation, and recalculation scheduling must be designed before derived inputs exist.

### Phase 3 synchronous benchmark

The offline SQLite benchmark uses deterministic persisted source snapshots and measures
both initial execution and idempotent replay. On the reference development machine:

| Rows | Transformation | Initial | Replay |
| ---: | --- | ---: | ---: |
| 100 | difference | 0.143 s | 0.025 s |
| 100 | moving average | 0.138 s | 0.024 s |
| 1,000 | difference | 1.266 s | 0.170 s |
| 1,000 | moving average | 1.268 s | 0.173 s |
| 10,000 | difference | 12.618 s | 1.663 s |
| 10,000 | moving average | 12.629 s | 1.676 s |

The 10,000-row cases stay below the 30-second synchronous safety gate on this
environment, while replay is materially cheaper. These measurements are not a
cross-platform latency guarantee; deployments should run the same benchmark against
their database before selecting request timeouts. A dedicated Analytics worker remains
the required next design step if production workloads cannot reliably satisfy the gate.

## Release acceptance criteria

MacroVision v0.7 is acceptable only when:

- all nine transformations conform to the contracts above using exact Decimal arithmetic;
- current and explicit as-of runs cannot observe future-ingested or future-revised data;
- every persisted output is traceable to exact immutable source versions;
- definition semantics, completed/failed runs, outputs, and lineage are immutable;
- identical snapshots replay deterministically and database races cannot duplicate work;
- input compatibility and missingness are explicit, with no resampling or substitution;
- resource bounds and private/public field separation are enforced;
- SQLite and real PostgreSQL migration, arithmetic, snapshot, and concurrency gates pass;
- upgrades from every previous revision preserve seeded legacy data;
- full offline tests retain at least 95% coverage;
- documentation and OpenAPI state that analytics are historical deterministic
  transformations, not recommendations or trading signals.
