# MacroVision Web v0.9 — Decision Intelligence architecture

## Product goal

v0.9 closes the largest gap between the existing MacroVision backend and the Persian Web product: the Decision Engine and portfolio evidence already exist as audited backend domains, but they are not yet usable from the Web.

The release adds a protected Decision Intelligence workspace for documenting falsifiable investment hypotheses, supporting and opposing evidence, independent criticism, invalidation rules, revisions, outcomes, and portfolio context. It remains decision support, not a signal engine.

## Non-negotiable boundaries

- No brokerage connectivity, order placement, automated trading, or personalized buy/sell recommendations.
- No AI-generated probability or confidence may silently overwrite a human decision record.
- Exact Decimal strings remain authoritative; browser numbers are presentation geometry only.
- Existing immutable decision revisions, evidence records, transactions, and snapshots remain the audit source of truth.
- GET readers never create mutations, provider synchronization, Analytics runs, portfolio snapshots, or decision revisions.
- Decision/portfolio routes remain authenticated. Mutations require the existing protected same-origin research/operator boundary.
- v0.8 public indicator eligibility remains independent and unchanged.
- v0.9 starts without a database migration; a migration is allowed only when a reviewed capability cannot be expressed safely with the existing schema.

## Approved Persian routes

v0.8 routes remain stable. v0.9 adds:

- `/fa/decisions` — protected decision-case index and completeness/status overview.
- `/fa/decisions/[decisionId]` — evidence dossier, critic review, invalidation conditions, revision timeline and explicit lifecycle actions.
- `/fa/portfolios` — protected portfolio index.
- `/fa/portfolios/[portfolioId]` — exact valuation, positions, cash, immutable transactions and snapshots.

Nested detail routes are not primary mobile-navigation items.

## Phase 1 — Decision reader

Use existing:
- `GET /api/v1/decisions`
- `GET /api/v1/decisions/{decision_id}`
- `GET /api/v1/decisions/{decision_id}/history`

Deliver:
- bounded list reader with Persian status labels;
- exact probability/confidence strings;
- evidence counts split supporting/opposing;
- explicit activation-completeness checklist;
- detail dossier and immutable revision timeline;
- loading, empty, error, 404 and terminal-state presentation;
- no mutation from reader render.

## Phase 2 — Decision lifecycle mutations

Use existing explicit POST endpoints for hypothesis, evidence, critic review, invalidation rule, revise, activate, invalidate and close.

Requirements:
- server-side actions only;
- same-origin and authenticated research/operator role checks;
- explicit confirmation for terminal lifecycle actions;
- domain 409 is shown as reload/reassess, never silently retried;
- probability and confidence remain separate six-decimal values;
- activation UI must mirror backend completeness gates but backend remains authoritative.

## Phase 3 — Portfolio reader

Use existing:
- `GET /api/v1/portfolios`
- `GET /api/v1/portfolios/{portfolio_id}`
- `GET /api/v1/portfolios/{portfolio_id}/summary`
- `GET /api/v1/portfolios/{portfolio_id}/transactions`
- `GET /api/v1/portfolios/{portfolio_id}/snapshots`

Deliver exact money/quantity strings, explicit unconverted foreign cash, allocations, realized/unrealized P&L, transaction history and snapshot history. No market-price provider is implied.

## Phase 4 — Portfolio mutations

Expose explicit protected actions for deposits, withdrawals, buys, sells, fees, dividends, interest, manual position price updates and snapshots.

The UI must preserve the backend's optimistic-concurrency and immutable-accounting rules. It must never imply that a recorded transaction was sent to a broker.

## Phase 5 — Decision ↔ portfolio context

Only after Phases 1–4 are stable, add a read model that can present decision evidence beside portfolio exposure without rewriting either domain. Any relationship added to persistence requires a dedicated migration and independent review. No automatic allocation recommendation is in v0.9 scope.

## UX system

- Persian RTL-first; codes, symbols, timestamps and exact numeric strings use LTR islands.
- Decision status is communicated with text + shape, never color alone.
- Supporting and opposing evidence receive equal visual weight.
- Critic review is a first-class panel, not hidden below supporting evidence.
- Invalidation conditions remain visible for active decisions.
- Terminal decisions are visually read-only.
- Dense tables retain accessible HTML alternatives to charts.
- Desktop and mobile share the same information hierarchy; mobile does not hide evidence.

## Security and publication

All v0.9 decision and portfolio surfaces are protected. None are added to the unauthenticated publication allowlist. NGINX, Next.js trusted-ingress checks, RBAC, CSRF/same-origin checks, rate limiting and no-store behavior continue to fail closed.

## Verification gates

Each phase requires:
- Ruff format/lint, mypy, backend tests and coverage gate;
- generated OpenAPI/client parity;
- frontend lint/typecheck/tests;
- production dependency audit;
- production build and deterministic smoke;
- responsive route smoke;
- no mutation during GET render;
- exact-head CI before squash merge.

v0.9 is not tagged until all approved phases are merged and the visual acceptance audit passes.
