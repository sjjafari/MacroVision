# MacroVision Web MVP v0.8 Architecture

## Product vision

MacroVision Web is an original Persian financial and macroeconomic research application.
It follows the general product model of professional financial portals, but it is not a
visual, structural, or textual clone of thefinance.ir or any other reference product.

The product combines:

- Persian macroeconomic dashboards;
- interactive market and economic charts;
- visible source and methodology context;
- historical, vintage-aware analysis;
- research transformations and point-level lineage; and
- educational and analytical content in later phases.

MacroVision remains an Investment Decision Intelligence Platform. The web application
helps users inspect evidence and documented calculations; it does not provide trading
signals, recommendations, or execution.

## Product principles

- Evidence comes before conclusions.
- Data and interpretation must remain visibly separate.
- The product has no trading-signal, order-execution, or brokerage behavior.
- Every important number should expose its source, knowledge cutoff, frequency, unit,
  and update time.
- Historical as-of views must be visibly distinct from current-data views.
- Data must never be silently interpolated, resampled, filled, or stitched.
- Exact Decimal strings returned by the API must be preserved.
- The interface must support mobile and desktop layouts.
- The interface is Persian and RTL-first.
- Accessible meaning must not depend on color alone.

## User types

### 1. Visitor / reader

- Reads dashboards and published analysis.
- Inspects series metadata, sources, freshness, and methodology.
- Has no mutation access.

### 2. Research user

- Compares series.
- Inspects transformations and historical vintages.
- Executes bounded research calculations in the private workspace.
- Is initially supported only in a trusted private environment.

### 3. Operator

- Manages data, derived definitions, runs, imports, and quality issues.
- Must never be exposed to public or untrusted users before authentication and
  authorization exist.

### 4. Administrator

- A future role responsible for users, permissions, deployment controls, and content
  management.

## Page specifications

### Home

The home page contains:

- a global header;
- market and macro summary cards;
- major recent changes;
- one featured economic chart;
- the latest updated indicators;
- methodology and source links; and
- an explicit data-update timestamp.

Summary cards must use a curated read model rather than browser fan-out to an
unbounded catalog.

Each summary metric is a backend-defined contract, not merely a value and label. It
must identify:

- the metric and its source-series or derived-definition identity;
- the selected observation or Analytics point identity;
- the exact Decimal value, unit, and frequency;
- the comparison type, comparison period, and comparison anchor;
- the previous or reference value and backend-computed absolute and percentage change;
- the observation timestamp, source knowledge cutoff, and derived-calculation cutoff;
- freshness and stale status;
- source attribution; and
- the Analytics run and definition-version identity when the metric is derived.

The browser must not calculate changes. Month-over-month, year-over-year, difference,
spread, ratio, and z-score metrics are produced by MacroVision Analytics. Persian copy
must state the comparison basis explicitly. Missing, stale, incomparable, and
frequency-mismatched states are distinct presentation states and must never collapse
to zero or an unlabeled blank.

### Macro dashboard

The dashboard uses a deterministic, reviewed configuration. It does not automatically
publish every database series.

Curated groups are:

- inflation;
- interest rates;
- labor market;
- economic growth;
- liquidity and money;
- yield curve;
- currencies;
- commodities and energy;
- financial conditions; and
- geopolitical risk.

### Indicator detail

The indicator page contains:

- Persian title and original title;
- series code;
- current value and change;
- unit, frequency, geography, and seasonal-adjustment status;
- source and latest update;
- an interactive time-series chart;
- explicit current and as-of modes;
- revision history;
- methodology;
- related derived series; and
- lineage access when the selected point is derived.

### Localized presentation metadata

The generic `metadata` JSON field is not a documented public presentation schema.
Before Phase 3, the web contract needs bounded, validated presentation fields for:

- `display_name_fa`;
- `original_name`;
- `description_fa`;
- a methodology summary;
- an optional localized unit label;
- source-attribution text; and
- an editorial update timestamp.

Canonical series code, unit, frequency, geography, and source identity remain
backend-owned domain fields and must not be overridden by localized presentation
content. The schema may be implemented as a dedicated curated catalog or explicit
series-presentation contract; the storage shape is intentionally not locked in this
architecture phase. Phase 2 may use private, seeded, reviewed labels while that public
contract is being built.

Phase 3A resolves the private portion of this gap with a bounded, code-reviewed catalog.
It stores Persian presentation, methodology, seasonal-adjustment presentation, source
attribution, an aware editorial timestamp, and ordered related-derived specifications.
Canonical series fields continue to come only from `DataSeries` and `DataSource`.
Configuration validation fails loudly, and no database migration is required.

The Phase 3A snapshot contract has two non-interchangeable modes. Current mode resolves
the latest effective observation and revision. Historical mode accepts only an aware
timestamp, normalizes it to UTC, and resolves both the current and previous observations
from information visible at that knowledge cutoff. Freshness is evaluated at generation
time for current mode and at the requested cutoff for historical mode.

Related-derived lookup is curated rather than inferred from formula text. It resolves
only configured canonical definition codes and returns the latest completed persisted
result for the exact latest definition version. It never executes Analytics or contacts
a provider.

### Publication visibility and curation

`DataSeries.is_active` is an operational ingestion/status flag. It is not permission
to publish a series. Public catalog eligibility requires a separate reviewed
publication or curation decision; authentication alone does not make unreviewed data
safe to publish. No series is exposed automatically merely because it exists or is
active.

The eventual public catalog layer must support an explicit, auditable publication
decision without conflating it with provider synchronization. Its database schema is
not locked here. Until it exists, Phase 2 dashboards use only a deterministic private
configuration containing reviewed series. The reviewed publication layer is required
before a visitor-facing catalog or dashboard is publicly deployed.

Phase 3A uses `reviewed_private` and `withheld` solely for private reader curation.
`reviewed_private` explicitly does not mean public eligibility. Withheld, unconfigured,
and nonexistent series share the same reader 404 behavior. Authentication remains
absent, so these contracts must stay on a trusted network. Phase 3B UI wiring and the
later auditable public-eligibility layer remain deferred.

### Compare

- A comparison contains at most four series.
- Frequency differences produce an explicit warning.
- The browser performs no implicit frequency conversion.
- Independent axes are allowed only when each axis is clearly labeled.
- Ratio and spread calculations must use MacroVision Analytics; they must not be
  reimplemented in the browser.

### Research workspace

The private research workspace supports:

- choosing source series;
- choosing one of the nine approved transformations;
- configuring typed parameters;
- running a bounded calculation through the explicit run endpoint;
- inspecting output and missing reasons;
- inspecting run metadata; and
- inspecting point-level lineage.

Save and share are deferred. Public access is prohibited until authentication and
authorization exist.

## Frontend technical architecture

The following decisions are locked for implementation phases:

- The repository remains a monorepo, with the frontend under `web/`.
- The framework is Next.js with the App Router.
- TypeScript strict mode is mandatory.
- Server Components compose pages and fetch initial read data.
- Client Components are limited to interactive charts and forms.
- TanStack Query synchronizes client-side server state.
- Apache ECharts renders interactive financial and macro charts.
- API types are generated from the MacroVision OpenAPI document.
- The frontend uses one typed API client and no duplicated handwritten response models.
- Browser requests use same-origin `/api/v1/*` paths.
- A reverse proxy or BFF mediates between the browser and FastAPI.
- The backend URL is runtime server configuration, not a public browser secret.
- Financial calculations must not use JavaScript `Number`.
- Decimal API values remain strings unless an explicit decimal library is used only for
  display-safe operations.
- UTC timestamps remain canonical; Persian calendar and locale formatting are
  presentation concerns only.
- Sensitive credentials are never stored in `localStorage`.
- The MVP has no service worker and no offline mutation queue.

### OpenAPI generation and drift control

Phase 1 introduces a repository script that imports the local FastAPI application and
exports its OpenAPI document without starting a provider synchronization, making a
live provider request, or requiring network access. The conceptual generated paths
are:

- `web/openapi/macrovision.openapi.json`; and
- `web/src/lib/api/generated/`.

The exact generator tool is selected during Phase 1, but generation must be
reproducible and must produce the TypeScript models and single typed client used by
the frontend. Handwritten duplicates of backend request or response models are
prohibited. CI regenerates the OpenAPI document and client and fails when the checked
in output differs. The frontend build therefore requires neither a running remote
backend nor provider credentials. Private Analytics fingerprints remain absent from
both OpenAPI and generated frontend types.

## Backend integration boundary

```text
Browser
  -> Next.js web application
  -> same-origin /api/v1/*
  -> transparent proxy to MacroVision FastAPI /api/v1/*
  -> PostgreSQL or SQLite
```

- FastAPI remains the system of record.
- `MACROVISION_BACKEND_URL` is a server-only runtime variable used by the transparent
  proxy; it is never emitted to browser code.
- The transparent proxy preserves the `/api/v1/*` path, query parameters, upstream
  status codes, safe error bodies, and exact Decimal strings.
- If web-specific orchestration is later required, it uses an explicit Next.js BFF
  namespace under `/api/web/*`; it must not masquerade as a FastAPI domain endpoint.
- Next.js must not duplicate Analytics rules or transformations.
- The frontend has no direct database access.
- The frontend and proxy contain no provider credentials.
- GET page requests never trigger Analytics calculations implicitly.
- Execution occurs only through
  `POST /api/v1/derived-series/{definition_id}/runs`.
- Public pages use read-only endpoints only.
- Mutation endpoints remain internal until authentication and authorization exist.

## Existing API mapping

All domain endpoints are currently mounted below `/api/v1`. `/health`, `/docs`, and
`/openapi.json` are system endpoints outside that prefix.

| Capability | Existing endpoint | Method | Contract notes |
|---|---|---:|---|
| Sources | `/api/v1/data-sources` | GET | Deterministic `limit`/`offset` list |
| Source detail | `/api/v1/data-sources/{source_id}` | GET | Existing read contract |
| Series list | `/api/v1/data-series` | GET | `limit`/`offset`; no catalog filters |
| Series detail | `/api/v1/data-series/{series_id}` | GET | Includes source and metadata fields |
| Raw observations | `/api/v1/data-series/{series_id}/observations` | GET | Paginated; no start/end bounds |
| Latest raw observation | `/api/v1/data-series/{series_id}/latest` | GET | One latest active observation |
| Historical raw observations | `/api/v1/data-series/{series_id}/observations/as-of` | GET | Required aware `as_of`; paginated |
| Raw revisions | `/api/v1/data-series/{series_id}/observations/{observation_id}/revisions` | GET | Immutable revision history |
| Derived definitions | `/api/v1/derived-series` | GET | Page envelope; enabled/code/prefix filters |
| Derived definition detail | `/api/v1/derived-series/{definition_id}` | GET | Current definition state |
| Definition versions | `/api/v1/derived-series/{definition_id}/versions` | GET | Immutable, paginated versions |
| Definition version detail | `/api/v1/derived-series/{definition_id}/versions/{version_number}` | GET | Exact version |
| Execute Analytics | `/api/v1/derived-series/{definition_id}/runs` | POST | Explicit bounded execution only |
| Analytics runs | `/api/v1/analytics-runs` | GET | Filtered, paginated run inventory |
| Analytics run detail | `/api/v1/analytics-runs/{run_id}` | GET | Persisted run metadata |
| Exact-run observations | `/api/v1/analytics-runs/{run_id}/observations` | GET | Start/end bounds and pagination |
| Latest derived observation | `/api/v1/derived-series/{definition_id}/observations/latest` | GET | Latest completed persisted result |
| Ranged derived observations | `/api/v1/derived-series/{definition_id}/observations` | GET | Start/end, version, and run filters |
| Historical derived observations | `/api/v1/derived-series/{definition_id}/observations/as-of` | GET | Knowledge-cutoff read with start/end |
| Point lineage | `/api/v1/analytics-runs/{run_id}/observations/{observation_id}/lineage` | GET | Exact point-level source lineage |
| Data-quality issues | `/api/v1/data-quality/issues` | GET | Paginated issue list |
| Data-quality issue detail | `/api/v1/data-quality/issues/{issue_id}` | GET | Current issue state |
| Data-quality history | `/api/v1/data-quality/issues/{issue_id}/history` | GET | Immutable event history |

List contracts use `limit` (1–200, default 100) and `offset` (default 0). Macro Data
values serialize as exact eight-decimal strings; Analytics output values serialize as
canonical Decimal strings. Public timestamps require an offset and normalize to UTC.
Private Analytics fingerprints are absent from responses and OpenAPI.

## Confirmed API gaps for the web MVP

| Gap | Confirmed state | Classification |
|---|---|---|
| Series search and minimum filters for code, category, geography, frequency, source, and active status | Raw series list currently accepts only `limit` and `offset` | Required before Phase 2 |
| Bounded raw observations by start/end date | Raw observation reads are paginated but have no date bounds | Required before Phase 2 |
| Batch summary/latest values with explicit metric semantics | Only one-series-at-a-time latest reads exist; no comparison contract exists | Required before Phase 2 |
| Curated dashboard configuration | No reviewed dashboard configuration contract exists | Required before Phase 2; private seeded configuration is acceptable |
| Localized presentation metadata and methodology | Generic metadata is not a validated public schema | Required before Phase 3 |
| Related derived-series lookup | Indicator detail cannot discover reviewed related Analytics | Required before Phase 3 |
| Multi-series comparison read model with explicit frequency and axis semantics | No aligned multi-series read model exists | Required before Phase 4 |
| Reviewed publication/catalog eligibility | `is_active` is operational and does not grant publication permission | Required before a public visitor catalog |
| Public-safe read-only API surface | Read and mutation routes share the same unauthenticated API | Required before public deployment |
| Authentication and role authorization | Not implemented | Required before public deployment |
| Rate limiting | Not implemented at the application boundary | Required before public deployment |
| CSRF strategy for mutations | Not defined because secure browser sessions do not yet exist | Required before public deployment |
| Production CORS/reverse-proxy policy | No CORS middleware or production proxy policy exists | Required before public deployment |
| Content/article API | No content domain exists | Deferred after MVP |
| Saved dashboards and comparisons | No persistence or API exists | Deferred after MVP |

The multi-series read model must expose observations without silently aligning,
resampling, filling, or converting frequencies. It is a Phase 4 comparison dependency,
not a prerequisite for the first curated dashboard. A simple page may perform bounded
parallel reads during development, but it is not the approved scalable comparison
contract.

## Security model

### Stage A: development and private research

- Runs on localhost or a trusted private network.
- The current API may be used by trusted operators and researchers.
- There is no public exposure and no untrusted user access.

### Stage B: public website

Before public deployment, MacroVision requires:

- public-safe read contracts and explicit publication eligibility;
- authentication;
- role-based authorization;
- separate public-read and operator-mutation permissions;
- secure, HTTP-only session cookies;
- CSRF protection;
- rate limiting;
- security headers;
- HTTPS;
- a configured reverse proxy;
- secret management;
- audit logging;
- backup and recovery;
- production PostgreSQL;
- strict origin restrictions; and
- no direct public exposure of FastAPI management endpoints.

## Testing strategy

- Frontend unit tests for formatting, state, and pure presentation helpers.
- Component tests for shared UI states and typed forms.
- API contract tests generated from or checked against OpenAPI.
- RTL layout tests.
- Automated accessibility checks.
- Chart tests for empty, missing, stale, and partial data.
- Screenshot or visual-regression tests for stable seeded views.
- End-to-end tests using deterministic seeded data.
- No live provider calls in normal tests.
- Installed-backend integration smoke tests.
- SQLite local integration tests.
- PostgreSQL CI tests.

## Delivery phases

### Phase 0: architecture and route/API map

Approve this document, product boundaries, security gates, and route mapping.

### Phase 1: frontend foundation

Add the `web/` scaffold, RTL design tokens, `AppShell`, offline local OpenAPI export,
generated API client, and CI drift enforcement. Browser reads use the transparent
same-origin `/api/v1/*` proxy configured by server-only `MACROVISION_BACKEND_URL`.

### Phase 2: read-only home and macro dashboard

Before Phase 2, provide deterministic reviewed dashboard configuration, a batch
summary/latest contract, bounded raw reads, minimum catalog filters, and the complete
summary-metric semantics defined above. Deliver curated summary cards and deterministic
dashboard groups. Private seeded and reviewed labels are acceptable during this phase.

### Phase 3: indicator detail

Before Phase 3, provide bounded localized presentation metadata, methodology content,
and a related-derived-series lookup. Deliver revisions, current/as-of modes, freshness,
source, and methodology views. The publication-eligibility layer may remain private at
this stage but is required before visitor-facing publication.

### Phase 4: comparison and derived visualization

Before Phase 4, provide the multi-series read model with explicit frequency and axis
semantics. Deliver bounded comparison and existing derived-series visualization.

### Phase 5: private research workspace

Expose typed transformations, bounded execution, output inspection, and lineage only in
the private environment.

### Phase 6: public security and deployment

Before any public deployment, provide public-safe reads, reviewed publication
eligibility, authentication and RBAC, secure sessions and CSRF protection, rate limits,
the configured proxy and origin policy, HTTPS, security headers, secret management,
audit logging, backups, and production PostgreSQL operations.

### Phase 7: content platform

Add the deferred magazine, editorial content, and subscription capabilities.

## MVP acceptance criteria

The first usable Web MVP must:

- run locally beside MacroVision 0.7.x;
- render Persian RTL pages on mobile and desktop;
- show deterministic seeded dashboard data;
- show at least one raw series and one derived series;
- support current and historical as-of reads;
- expose source and freshness;
- expose lineage for a derived point;
- preserve exact values;
- make no provider network request during tests;
- contain no trading-signal or recommendation language;
- pass frontend and backend CI; and
- remain private until authentication gates are complete.

## Non-goals

- Broker integration.
- Order execution.
- Automated trading signals.
- AI-generated recommendations.
- Portfolio optimization.
- A social network.
- A native mobile application.
- Arbitrary user formulas.
- Derived-to-derived Analytics.
- Automatic data interpolation.
- Public deployment before security gates are complete.
